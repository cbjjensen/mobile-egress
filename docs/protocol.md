# Tunnel protocol

## Transport

Relay, Windows, and Android sessions use WebSocket over TLS with certificate authentication after enrollment. Enrollment uses the same TLS endpoint with a single-use pairing capability before a client certificate exists.

## Envelope

Every binary message is a length-delimited JSON envelope:

```json
{
  "version": 1,
  "type": "open|opened|rejected|data|close|ping|pong",
  "streamId": "uuid-or-empty",
  "payload": "base64url-encoded-bytes"
}
```

`open` payload is a destination IP, TCP port, and client identity generated by the relay after destination validation. `data` is opaque TCP data. `close` includes only a finite protocol error code. A peer rejects unknown versions, unknown message types, invalid stream IDs, oversized frames, and role-incompatible messages.

## Stream lifecycle

1. Windows receives a SOCKS5 `CONNECT` request and sends the requested host and port to the relay.
2. Relay resolves/validates the destination and creates a stream ID.
3. Relay sends `open` to Android; Android validates the IP, binds a socket to cellular, then replies `opened` or `rejected`.
4. Relay returns SOCKS success only after `opened`.
5. Both peers exchange ordered `data` frames until either sends `close`.

The relay applies per-client and per-agent stream limits. It sends `close` on session loss, timeout, revocation, policy rejection, or failed target connection.
